# spark-hbo — прототип history-based оптимизации для Apache Spark

Минимальное воспроизведение первого «приложения» из Ultron (Databricks, VLDB 2026)
на open-source Spark 3.5.3, без патча ядра: **выбор broadcast join по реальному
размеру подплана, запомненному с прошлого запуска**.

## Идея

Без статистики Spark оценивает `Filter` как размер всего файла. Отфильтрованный
справочник весом в килобайты выглядит как 86 МБ, это больше порога broadcast
(10 МБ), и строится sort-merge join. AQE ошибку исправляет, но поздно: к моменту,
когда стадия справочника материализовалась, факт-таблица уже отшаффлена.
И так в каждом запуске, потому что памяти между запусками у AQE нет.

HBO закрывает петлю обратной связи:

```
запуск N:   план SMJ → AQE видит 31 KB → переключает на BHJ → листенер пишет [отпечаток подплана → число строк]
запуск N+1: строки × ширина строки ≤ порога → BROADCAST-хинт → план сразу BHJ, факт не шаффлится
```

## Компоненты

| Файл | Что делает |
|---|---|
| `Fingerprint.scala` | Ключ подплана: SHA-1 от `canonicalized.treeString` (Catalyst нормализует exprId) + пути файлов источников + «фактор размера» `floor(log2(сумма входов))` для инвалидации при росте данных. Литералы входят в ключ (literal-sensitive, как в Ultron). |
| `HboListener.scala` | `QueryExecutionListener`: после запроса обходит финальный план AQE, берёт материализованные shuffle- и broadcast-стадии и их runtime-статистику (ту же, по которой решает AQE), через `logicalLink` находит логический подплан и пишет отпечаток → число строк. |
| `HboJoinRule.scala` | Правило оптимизатора: для equi-join без пользовательских хинтов смотрит историю сторон; размер считает как строки × ширина строки по схеме (как оценщик Spark); если он ≤ `autoBroadcastJoinThreshold`, а оценка Spark выше порога, ставит `BROADCAST`. Учитывает, какую сторону разрешает транслировать тип джойна. |
| `HistoryStore.scala` | История в памяти драйвера + TSV-файл, переживает перезапуск приложения. |
| `Hbo.scala` | Точка входа, счётчики (shuffle bytes, число вмешательств), отчёт о последнем запросе. |

Правило регистрируется в `spark.experimental.extraOptimizations`, это **последний**
батч оптимизатора. Поэтому оно видит ровно тот логический план, который уходит
в физическое планирование, и отпечатки при чтении совпадают с записанными.
(Через `SparkSessionExtensions.injectOptimizerRule` правило попало бы в середину
пайплайна, и последующие правила меняли бы дерево.)

## Результаты (local[4], fact 20M строк, dim 2M строк, 3 прогона)

| | время | shuffle write |
|---|---|---|
| AQE | 6.76 s | 255.4 MB |
| AQE + HBO (после 1 обучающего запуска) | 1.74 s | ~0 MB |

На малом наборе (2M × 400k) разница 1.96 s → 0.83 s. В отчёте видно, что без HBO
исходный план — SMJ, финальный — BHJ (AQE «чинит» на лету); с HBO уже исходный
план — BHJ.

Это иллюстрация механизма, а не бенчмарк: сценарий подобран так, чтобы ошибка
оценки была максимальной.

## Запуск

```bash
pip install pyspark==3.5.3        # версия должна совпадать с build.sbt
sbt package
python bench.py --jar target/scala-2.12/spark-hbo_2.12-0.1.jar
# поменьше данных: --fact-rows 2000000 --dim-rows 400000
```

Подключение в своём коде:

```python
spark._jvm.hbo.Hbo.install(spark._jsparkSession, "/tmp/hbo-history.tsv")
```

## Расширенный замер: цена исправления AQE

`bench.py` пишет каждый прогон строкой в `results.csv`, а разбивку по стадиям в
`results-stages.jsonl`. В сводке печатаются медианы:

| Колонка | Что это |
|---|---|
| `wall_s` | время запроса |
| `task_time_s` | суммарное время всех задач (работа кластера, не зависит от параллелизма) |
| `shuffle_write_mb`, `shuffle_write_s` | сколько записано в shuffle и сколько времени ушло на запись |
| `shuffle_local_read_mb`, `shuffle_remote_read_mb` | shuffle, прочитанный локально и по сети |

«Цена исправления AQE» = AQE минус AQE + HBO, по `wall_s` и по `task_time_s`.

Серии для эксперимента «цена исправления vs параллелизм»:

```bash
python bench.py --label local4                                 # базовый
python bench.py --master 'local[*]' --label local-all          # все ядра, один процесс
./cluster.sh start 4 2 3g                                      # 4 worker'а × 2 ядра
python bench.py --master spark://127.0.0.1:7077 --executors 4 --executor-cores 2 \
    --executor-memory 2g --host-local-read off --label sa-4w
python bench.py --master spark://127.0.0.1:7077 --executors 4 --executor-cores 2 \
    --executor-memory 2g --host-local-read off --local-reader off --label sa-4w-no-lr
./cluster.sh stop
```

Два флага, без которых цифры на одной машине обманывают:

- `--executors N` — ждать, пока зарегистрируются все executor'ы. Иначе первые запросы
  идут на часть кластера.
- `--host-local-read off` — по умолчанию Spark 3.x читает shuffle-блоки соседних
  executor'ов на том же хосте прямо с диска и считает это локальным чтением. На одной
  машине из-за этого сетевое чтение всегда ~0. Флаг выключает это, и блоки идут через
  сеть (loopback), как между разными машинами.

Пробный прогон (малые данные, 3 worker'а × 1 ядро, `--host-local-read off`): из 25,6 МБ
shuffle факта по сети читалось 17–19 МБ, то есть около (N−1)/N, как и ожидается при
равномерном раскладе; с HBO — 0. Наблюдение для проверки: local shuffle reader почти
не уменьшил сетевое чтение — надо разобраться, сработал ли он в этом плане.

## Протухание истории (`drift.py`)

```bash
python drift.py
```

Обучаемся на справочнике, где фильтр почти всё отсекает, затем по тому же пути кладём
справочник, где фильтр пропускает все строки, а размер файлов тот же (27,0 МБ → 27,0 МБ,
фактор размера в ключе не меняется). Результат:

| Запуск | Хинт | План | Что произошло |
|---|---|---|---|
| v1 learn | нет | SMJ → BHJ | AQE чинит план, история записана |
| v1 with history | broadcast | BHJ | история сработала |
| v2 run 1 | broadcast | BHJ | **устаревшая** история: транслируется вся сторона (~12 МБ, больше порога) |
| v2 run 2 | нет | SMJ | листенер записал новый размер — хинт больше не ставится |
| v2 run 3 | нет | SMJ | стабильно |

До исправления листенер не записывал размеры broadcast-стадий, и после первого
применения история по справочнику замораживалась: в v2 broadcast ставился бы всегда.

Размеры shuffle- и broadcast-стадий в разных единицах (сериализованные байты и память
хэш-таблицы, минимум ~1 МБ даже для сотни строк). Поэтому в истории хранится число строк,
оно одинаково у обеих стадий.

## Замер на TPC-DS

```bash
pip install duckdb
python gen_tpcds.py --sf 10 --out /tmp/tpcds-sf10        # данные, один раз (10–20 минут)
python tpcds_bench.py --data /tmp/tpcds-sf10 --queries q3,q7,q19   # проверка на трёх запросах
python tpcds_bench.py --data /tmp/tpcds-sf10                       # все 103 запроса
```

Для каждого запроса: прогрев, затем режимы `noaqe` (статический план), `aqe`, `hbo`
(обучающий запуск + замер). Строка на прогон — в `tpcds_results.csv`, в конце сводка:
суммарное время и shuffle по режимам, в скольких запросах AQE переключал SMJ → BHJ,
сколько из этого убрала история, топ-10 запросов по выигрышу.

Запросы (вариант под Spark SQL) скачиваются из репозитория Apache Spark v3.5.3 в
`tpcds-queries/`. Таблицы регистрируются как временные представления над parquet без
статистики — это и есть случай лейкхауса.

Масштаб важен: на SF1 справочники TPC-DS крошечные, Spark сразу выбирает broadcast,
и ошибка оценки почти не возникает. Осмысленные цифры начинаются с SF10, лучше SF100.

### Первые цифры (SF10, local[4], порог broadcast 10 МБ)

Пока прогнана часть запросов: 16 из 103 (q1, q2, q3, q4, q6, q8, q10, q11, q14a, q14b,
q17, q23a, q23b, q24a, q64, q72), по одному замеру на режим. Сырые данные:
`tpcds_results.csv`, вывод прогона: `tpcds_sf10_top.log`.

| | noaqe | aqe | aqe + hbo |
|---|---|---|---|
| суммарное время | 130.9 s | 113.3 s | 103.4 s |
| суммарный shuffle write | 10 659 MB | 10 605 MB | 8 448 MB |

- AQE переключал SMJ → BHJ в 12 запросах из 16.
- HBO поставил broadcast-хинты в 8 запросах.
- Больше всего выиграли q14a (−3.1 s), q14b (−2.4 s), q4 (−1.8 s), q23b (−1.2 s).

Это предварительно: один прогон, без разброса, малая выборка запросов.

## Известные ограничения (и где здесь исследование)

1. **Только точные повторы.** Изменился литерал — другой ключ. Следующий шаг:
   уровни отпечатков (без литералов / по форме плана), как в Ultron, или k-NN по
   признакам подплана, как в PostgreSQL aqo. Это и есть проблема холодного старта.
2. **Подпланы после перепланирования AQE пропускаются.** Если в логическом дереве
   уже есть `LogicalQueryStage`, отпечаток не совпадёт с исходным планом. Поэтому
   история пишется в основном для «листовых» стадий (скан + фильтр + проекция).
   Для джойна поверх джойна нужен отпечаток, устойчивый к замене стадий.
3. **Агрегаты записываются по размеру частичной агрегации** (shuffle идёт после
   partial aggregate), то есть с завышением. Это безопасно, но broadcast иногда
   упускается.
4. **Байты оцениваются по схеме.** Размер стороны = строки × ширина строки по
   схеме (`EstimationUtils.getSizePerRow`). Для строк переменной длины это грубо;
   для строгих гарантий против OOM нужен запас.
5. **Нет отката.** Если broadcast оказался хуже (перекос, изменились данные
   в пределах того же фактора размера), правило не узнает. Нужен детектор
   регрессий (aqo отключается через 50 неудачных итераций, BigQuery — по confidence).
6. **Хранилище — один процесс.** Для кластера/нескольких приложений нужен общий
   стор и асинхронная запись (push-модель Ultron).
